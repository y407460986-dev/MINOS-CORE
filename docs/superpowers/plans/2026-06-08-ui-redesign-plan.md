# MINOS-CORE 桌面端 UI 全面重设计划

> 用 taste-skill 的方法论分析后产出。范围：交互+视觉全面重设 + 深色模式 + 全部 5 个页面。
> 日期：2026-06-08

---

## 一、Design Read（产品定位，一句话）

> 面向制造业质量工程师的 **APQP 三表生成桌面工具**。用户是 B2B 专业用户（产线/质量部门），核心诉求是**信息密度、可信度、操作效率、数据可读性**——不是"好看"，是"专业、可靠、不出错、看得清"。

关键约束（决定了不能套用花哨的营销页审美）：
- 这是**多步骤产品 UI + 数据表格 + 仪表盘**，taste-skill 默认技能明确不覆盖此类，只借用其"反模板审计 + 三维度调节"方法论。
- 长时间盯屏作业 → 深色模式是刚需。
- 数据正确性 > 视觉惊艳。任何重设不能牺牲信息密度和可扫描性。

---

## 二、现状评估（基于代码审计）

### 已经做得好的（要保留，不要推翻）
- 完整的设计系统：`globals.css` 有成体系的 CSS token（背景/前景/语义色/surface 层次/动效曲线/reduced-motion 适配）。
- 体系化组件库：`experience.tsx` 提供 Surface/Notice/StatusPill/ContextPanel/EmptyState。
- shadcn/ui + Tailwind，组件规范；Geist/Inter 字体，6px 圆角，黑色 CTA——专业工具调性正确。
- 信息架构清晰：侧栏 5 页（工作台/导入/评审/导出/设置）+ Toolbar + 主区。

### 真实可改进点（重设的靶子）
1. **信息层次偏平**：工作台状态栏 `运行#/状态/记录/高风险/待确认/已确认` 全是同号灰字并排，高风险数不够醒目。
2. **数据表格可读性**：三表是核心，风险色编码、行选中态、可扫描性是工程工具命脉，值得专门打磨。
3. **状态反馈散落**：`saveState` 是纯文本塞在角落，缺统一反馈体系（toast/进度）。
4. **无深色模式**：token 只有亮色，`globals.css` 缺 `.dark` 变体。
5. **响应式硬约束**：`body { min-width: 1080px }` 写死，无自适应。
6. **导入页双栏检查器信息密集**：右栏多个 `dl` 堆叠，缺视觉分组节奏。

## 三、设计方向（taste-skill 三维度调节）

| 维度 | 取值 | 理由 |
|------|------|------|
| VARIANCE（变化度） | **低** | 工程工具要一致、可预测，不要花哨布局 |
| MOTION（动效） | **克制** | 仅状态反馈/过渡，复用现有 motion token，尊重 reduced-motion |
| DENSITY（密度） | **高** | 专业用户要在一屏看到尽量多的有效信息 |

视觉语言：延续 Vercel ink-on-paper，但**强化层次**（字重/字号对比、surface 分层、语义色权重），新增完整深色主题。

## 四、执行计划（分阶段，每阶段可独立验证）

> 原则：手术刀式改动，保留信息架构，先地基后页面。每阶段结束跑 `npm run build` + 目视验证。

### 阶段 0：地基——双主题 Token 系统（最高优先级）
- 在 `globals.css` 新增 `.dark` 选择器下的全套 token（背景/前景/surface/语义色/border 的深色取值）。
- `tailwind.config.js` 增加 `darkMode: "class"`。
- 新增主题切换：`ThemeProvider` + localStorage 持久化 + 跟随系统（`prefers-color-scheme`）。
- Toolbar 加亮/暗切换按钮。
- **验证**：切换主题，5 个页面无对比度问题、无硬编码颜色漏网（重点查 `bg-white`、`text-[#...]` 这类写死的）。

### 阶段 1：清理硬编码颜色
- 全局搜 `bg-white`、`bg-[#...]`、`text-[#6f4e00]`、`shadow-[...rgba...]` 等绕过 token 的写法，替换为语义 token。
- 这是深色模式能成立的前提。
- **验证**：grep 确认无漏网；亮/暗都正常。

### 阶段 2：工作台（ThreeTableWorkbench）——核心页面
- 状态栏重设：高风险/待确认用语义色 + 字重强化层次，不再全灰并排。
- 三表 WorkbenchTable：强化风险色编码、行选中态、表头吸顶、斑马纹可选。
- 统一状态反馈：把 `saveState` 文本升级为统一的 toast/进度条体系。
- **验证**：有数据/无数据/生成中/失败 四态都正确；表格可扫描性提升。

### 阶段 3：导入页（DrawingImportPage）
- 双栏检查器加视觉分组节奏（分隔、留白、小标题层次）。
- StatusRail/Surface 在深色下校准。
- **验证**：idle/running/active/success/failed 五态正确。

### 阶段 4：其余三页（评审/导出/设置）
- ReviewClosurePage、ExportPage、SettingsPage 统一到新视觉语言。
- 复用 experience 组件，保证跨页一致性。
- **验证**：逐页亮/暗目视 + build。

### 阶段 5：响应式与收尾
- 放宽 `min-width: 1080px`，给中小屏合理降级（侧栏可收起等）。
- 全局动效一致性检查，reduced-motion 复核。
- **验证**：缩放窗口无溢出；完整 `npm run build` 通过。

## 五、不做的事（控制范围）
- 不改后端 API、数据模型、业务逻辑。
- 不替换 shadcn/Tailwind 技术栈。
- 不改信息架构（5 页结构、链式流程不变）。
- 不引入新的重型依赖（主题切换用现有能力实现）。

---

## 六、风险与注意
- **深色模式最大风险是硬编码颜色漏网**——阶段 1 必须彻底，否则暗色下会出现白块/黑字不可读。
- 表格重设要保证**不丢信息密度**，专业用户反感"留白过多看得少"。
- 每阶段独立验证，避免一次性大改难回滚。
- taste-skill 只作方法论参考，**不直接套用其落地页代码骨架**（GSAP 动效等不适合本工具）。

---

## 七、建议的推进方式
- 阶段 0+1（地基）先做，这是深色模式和后续所有页面的前提，且风险可控、见效明显。
- 之后按页面优先级推进：工作台（用户停留最久）→ 导入 → 其余。
- 可用并行子代理分页面改，但**同一文件串行**，每批后 build 核对。
